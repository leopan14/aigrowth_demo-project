PART 1 AI Native 范式 概念锚定 · 三原则 · 用户价值感知
1.1 谁是机长 — AI Enabled vs AI Native
维度AI EnabledAI Native
谁是机长人是机长,AI 是副驾AI 是机长,人在塔台
流程结构固定流水线,关键节点人工卡点事件驱动的 Agent 协作网络
人的位置Human-in-the-Loop(人在流程中)Human-on-the-Loop(人在边界) + Human-at-the-Result(人在结果)
验证范式依赖真实人类样本(访谈、复盘)数字孪生 Persona 池 + 自动小流量影子验证
当人不在场系统降级,不能继续高质量运行系统照常自驱动运行,人到场只为审阅边界事件
关键区分: AI Enabled 与 AI Native 的本质差异,不在 "AI 做了多少事",而在 "谁是机长"。 V2.0 是后者。
1.2 V2.0 三原则
原则 ①
目标驱动
客户只表达增长意图(由系统解析为可量化目标),不是配置项;系统内部自主拆解、规划、执行
原则 ②
人在边界
人不在流程中,而在边界条件中(红线、预算、品牌底线);红线触发熔断,非红线由 Agent 自决策
原则 ③
自验证闭环
AI 输出不可直接执行,必须经 Persona 池或影子流量验证;每个生成式 Agent 都内置 Critic 子模块
关于原则 ③ 的产品诠释: "自验证"不只是单点防错,更核心的是 — Agent 自驱动 perceive→plan→act→reflect 循环 + 自学习提升 → 让专家有计划地退场。这是 V2.0 能否成立的产品 hypothesis,也是 AI Native 区别于 AI Enabled 的根本承诺。
1.3 用户价值感知 — 客户能感知到的 6 条承诺
价值 ①
意图 in,结果 out
客户只表达增长意图和边界条件,系统自动解析为可量化目标;不再做画像配置、场景设计、创意审核
价值 ②
7×24 自驱动
专家不在场也能跑,不退化、不停摆;半夜出现的机会窗口系统能自己接住
价值 ③
专家逐步退场
客户越用越省心,从"我得审"到"我只看结果"——这是产品有计划的能力曲线
价值 ④
冷启动加速 · 经验前置
新客户不必从零开始——平台已沉淀的同行行业经验(模板 / Persona / 潜客库)直接复用,启动周期从月级压缩到周级
价值 ⑤
决策可重放 + 24h 回滚
任何决策都能事后还原"当时系统看到了什么";做错了能在 24 小时内一键回滚
价值 ⑥
合规可审计
不可篡改审计日志,监管面前能解释每一笔触达、每一次决策的依据
PART 2 六层架构 → 产品定位与核心能力 每一层都为产品贡献了某种能力
L1 · 接入层 Access Layer
客户接触面 = "意图 in / 结果 out" + 异常审阅 + 一键回滚
客户与系统交互的唯一入口。客户在这里只做三件事:表达增长意图、设置边界条件、查看结果与告警。把意图细化为可量化目标(OKR)是 Planner 在编排层做的事,不需要客户自己懂行业基准。客户不需要定义画像、设计场景矩阵、配置渠道、审核创意——这些 AI Enabled 范式中的人工动作全部内化为系统能力。对应价值卡片 ① + ⑤。
关键组件 目标解析器 客户仪表盘 API 网关
L2 · 编排层 Orchestration
"动态规划,新行业不改流程"——Planner 看不同状态做不同 DAG
编排层只有一个 Planner Agent 和一个 Executor,承担传统流水线的全部协调职责。和固定流水线的核心区别:Planner 根据当前 World Model 状态动态生成 DAG——新行业不改流程,只是 Planner 看到不同状态做不同的规划。对应价值卡片 ②。
关键组件 Planner Agent Executor Event Bus
L3 · 智能体层 Agent Layer
"12 个自主智能体网状协作,每个 Agent 自带 Critic"
12 个 Agent 按职责分为五类。每个 Agent 都遵循统一接口契约:输入 → Critic 自评 → 输出 + 不确定性 + 可回滚。协作是网状的而非树状的——Planner 处于中心调度位,但其他 Agent 可以直接通过 Event Bus 互相通信;Resolver 和 Compliance 横切监督所有执行类 Agent。对应价值卡片 ②③。
关键组件 战略 / 数据 / 用户 / 执行 / 治理 五类 Agent
L4 · 世界模型层 World Model
"时间旅行 / 一致性快照 / 决策可重放"
World Model 是所有 Agent 共享的"现实"。它不是数据库,而是事件溯源系统——所有 Agent 输入都来自某个快照,所有输出都作为事件写回 Event Log。这种架构带来三个能力:回到任意时刻调查 / 避免读到中间态 / 精确还原每次决策时 Agent 看到的世界。对应价值卡片 ⑤。
关键组件 World Model Store State Snapshot Identity Graph
L5 · 数据资产层 Data Assets
"跨客户数据飞轮,平台核心护城河"
六类数据资产协同构成数据飞轮:行业潜客库、客户项目库、脱敏回流标签库、行业模板库、行业知识图谱(支持 GraphRAG)、Persona 池(LLM 合成 + 真实流量校准)、实验沙盒。客户越多 → 数据越多 → 模板越准 → 新客户冷启动越快——这是飞轮的底层机制;对客户而言,这意味着冷启动加速、经验前置。对应价值卡片 ④。
关键组件 行业潜客库 Persona 池 行业知识图谱 行业模板库 实验沙盒 脱敏回流标签库
L6 · 治理层 ⟂ Governance (横切)
"自由地跑、严格地控"——Policy-as-Code 让 Agent 自由决策的同时严守红线
传统 RPA 靠人在流程节点审批,V2.0 靠 Policy + Observability + Kill Switch 三件套实现"自由地跑、严格地控"。所有治理规则(合规、频控、降级、模板治理、追溯成熟度)写成 Policy-as-Code,由 Policy Engine 在每次 Agent 决策前自动评估。对应价值卡片 ⑥。
关键组件 Policy Engine Observability Audit Log Kill Switch

PART 5 落地路径与 KPI 体系 产品落地思路 · 只给 KPI 主轴,不展开 MVP / 阶段 / 资源
5.1 框架命题:V2.0 客户价值兑现地图
借鉴锚点 参考资料 V1.0 docx · 「客户价值兑现地图」+「MVP 实施路径与验收标准」—— 客户视角的 KPI 组织框架,V2.0 范式下重写适配
V2.0 是面向客户的商业化产品,KPI 体系必须从"客户每个阶段能看到什么具体价值"倒推。本节借鉴 V1.0 参考文档的客户视角框架,V2.0 范式下重写为 MVP-1 → MVP-5 五阶段的客户感知交付物地图;并附 6 条客户视角验收标准,作为各阶段必须通过的硬性标准。
5.2 客户价值兑现地图(MVP 阶段化)
阶段系统完成什么客户能看到什么具体价值
MVP-1
意图对齐		 Planner Intake 解析「意图对象」+ Initial Plan 反推 OKR(预算 × 时间窗 ÷ 行业基准 CPL)+ L1 仪表盘上线 一份意图 → OKR 解析文件(含漏斗倒推依据)+ L1 仪表盘可调整目标
MVP-2
影子验证		 Persona 池预验证 + 1-5% 影子流量观测 + Critic 子模块对生成结果自评 Persona 反应报告(LLM 合成虚拟用户的反应汇总)+ 影子流量 vs 基准的业务效果对比
MVP-3
自驱动试运行		 主流量执行 · 7×24 自驱动 · 24h 回滚窗口可用 · Event Sourcing 决策可重放 7×24 自驱动期间的业务指标(线索/SQL/转化)+ 任意时刻决策回放报告
MVP-4
飞轮启动		 跨客户经验调用(行业模板库 / 同行 Persona / 行业潜客库 D0→D2 渐进) 冷启动周期缩短证据(月 → 周)+ 跨客户经验贡献回溯报告
MVP-5
专家退场		 全自驱动稳态 + 销售证据包闭环 + 叠加贡献追溯自动化 「专家介入率下降 vs 业务效果不衰减」双指标 + 销售证据包(每条 AI 触达)+ 增长复利追溯
客户视角验收 6 条 V2.0 必须通过的客户视角标准
  1. 客户早期可见价值 —— MVP-1 即看到 OKR 反推 + 仪表盘
  2. 销售愿意采纳 —— 每条 AI 触达带证据包 + 反馈入口
  3. 增长结果可追溯 —— 有效线索回溯到定位 / 场景 / 信号
  4. 人工缺席可降级 —— 关键审批缺失时保守运行,不失控放大
  5. 评分不是黑盒 —— timing_score 有版本 / 探索流量 / 回滚机制
  6. 场景假设可验证 —— P0 场景至少一项 Persona + 影子流量证据
PART 6 核心命题与挑战 不展开 MVP,但抛出问题 + 给应对建议
6.1 核心命题:自驱动学习的产品 hypothesis
Agent 自学习提升 + 专家有计划退场 = V2.0 产品价值的核心断言。
这不是难题,而是 V2.0 能否成立的产品 hypothesis 本身。命题成立与否,直接决定 V2.0 是 AI Native 还是退化为 AI Enabled。
应对方向 用 Part 5「客户价值兑现地图」MVP-1 → MVP-5 各阶段交付物的持续兑现,作为 hypothesis 成立的客户感知凭证;Reflection 学习闭环输出 A/B 验证后上线;Persona 池 + 影子流量做小流量预验证(对应 docx 原文「自学习沉淀」机制)。
6.2 实施挑战与应对建议
除核心命题外,V2.0 落地中还存在几类固有挑战。这些不是 V2.0 的"缺陷",而是 AI Native 范式必须正面应对的边界条件;docx 已为大部分给出应对机制,此处汇总以便老板 review。
#挑战简述我们的应对建议
1 🟡 冷启动悖论 Agent 自学习靠数据沉淀;冷启动期没有数据,必然要专家先行 早期专家定义"模板候选"做 baseline;Persona 池替代访谈样本;行业库 D0→D2 渐进;接受"早期一定有专家成本"的事实
2 🟡 学习闭环失效风险 Reflection 自动归因 / 权重学习如果失效,V2.0 命题破产 学习闭环带来的指标提升做明确量化;Reflection 输出 A/B 验证后才上线
3 🟡 LLM 幻觉 产品 / 价格 / 承诺类幻觉直接影响客户体验 Critic 子模块 + Persona 预验证 + 24h 回滚窗口 + Kill Switch(docx 6.5 已规定)
4 🟡 合规与回流污染 数据回流到平台库可能跨客户污染;GDPR / PIPL 合规 Compliance 三层规则 + 不可篡改审计日志 + 灰度沉淀 + 模板版本回滚
